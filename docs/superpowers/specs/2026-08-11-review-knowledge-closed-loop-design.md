# 交易复盘知识闭环优化设计

日期：2026-08-11

状态：方案 B 已批准，书面规格待复核

目标用户：已经熟悉产品、每天高频复盘的独立交易员

平台范围：仅 Windows 客户端与 macOS 客户端

## 1. 结论

当前产品已经能完成交易记录、正文复盘、案例提炼、周复盘和随机复习，但它们更像一组彼此相邻的功能，而不是一条连续的知识生产链。前半段“发现问题—写下内容—保存案例”基本可用，后半段“对比—形成规则—在下一次决策前找回规则”存在明显断点。

本设计采用已批准的方案 B“案例内薄闭环”：

- 保留现有七项工作台主导航，不新增顶级页面；
- 以案例详情作为知识加工中心，但不把它改造成复杂工作流；
- 用显式来源、短暂路由上下文和合理默认值完成阶段交接；
- 用两条案例的只读对比层完成对比，不建立对比项目或新实体；
- 复用周复盘现有的单一承诺，不建立规则中心或规则候选库；
- 扩展现有全局搜索，让沉淀内容可以被再次找到；
- 先修正状态真相和数据可解释性，再增加入口与快捷动作。

目标不是让每个阶段都有一个功能，而是让用户在一次连续复盘中始终只回答交易问题，不需要判断“接下来应该去哪一个模块”。

本设计基于：

1. Windows Electron 隔离实例黑盒走查；

4. 桌面目标浏览器内部契约 17/17 通过；
5. Electron 存储协议检查 25/25 通过；
6. 既有复盘减负、来源同步和桌面体验设计文档。

Windows Electron 已稳定复现两个前段断点：

- “错过的机会”只有模块跳转，没有在当前语境记录错过的入口；
- 从该页前往案例记录后，新案例仍默认“优秀范例”，没有继承“错过机会”。

后半段 Electron 补验另建立最小 UI 数据，四项均 2/2 失败，且控制台错误与 page error 均为 0：

- 选中两条案例后只有复制和删除，没有对比；

## 3. 当前闭环审计

| 阶段 | 当前可用能力 | 主要断点 | 设计判断 |
| --- | --- | --- | --- |
| 发现问题 | 今日待复盘、平仓、错过机会、随记 | 平仓后只有撤销；错过页只能跳模块；随记无法交接 | 不新增收件箱，在现有发现面就地给出下一步 |
| 记录案例 | 新建案例、从交易提炼案例 | 新建只根据路径猜类型；上下文丢失；同源可重复提炼 | 发起动作携带显式上下文；同源默认幂等 |
| 补充证据 | 富文本、图片、来源交易只读快照 | 随记证据不能追溯；来源缺失语义不统一 | 保留“来源证据 / 案例洞见”双层结构，不建证据实体 |
| 分类判断 | 案例类型、掌握状态、错误标签、旧复盘分类 | 多条分类轴重叠，更新入口不同，状态可漂移 | 案例界面只保留三条规范轴；旧字段只兼容 |
| 对比复盘 | 单条详情、单条随机复盘 | 无两条对齐、无差异呈现、无返回上下文 | 两条为固定上限，在当前工作区打开只读对比层 |
| 沉淀规则 | 周复盘承诺与验收条件 | 与来源案例无关联；仅能在下一次周复盘看到 | 复用单一承诺，只补来源 ID 和上下文交接 |
| 检索复用 | 命令面板、列表筛选、保存视图 | 搜索语料窄，案例与交易不区分，承诺和随记不可搜 | 扩展本地索引与结果分组，不建搜索后端 |

## 4. 设计原则

### 4.1 上下文交接优先于新增入口

一次动作产生的来源、分类、筛选和返回位置由软件自动携带。用户只做业务上无法推断的判断，例如“这次错过属于实盘、模拟还是知识案例”。

### 4.2 默认值必须可解释

默认值来自明确来源或当前唯一筛选，不从宽泛路径、自由搜索词或历史偶发设置猜测。无法可靠推断时沿用现有安全默认，不制造“看似智能、实际错误”的自动填写。

### 4.3 只有一个事实写入点

案例类型、掌握状态和兼容分类必须通过同一个规范化函数写入。筛选、随机复盘和详情页不得各自解释同一状态。

### 4.4 保存成功先于状态跳转

完成复盘、提炼案例、进入下一条都不能让未落盘正文丢失。任何保存失败都停留原地，说明失败对象和可执行的恢复动作。

### 4.5 克制地保留必要摩擦

不能静默推断的业务事实保留一次紧凑选择；不能为了追求“一键”而写错交易类型、绕过周统计或制造虚假的学习状态。

## 5. 信息架构与完整旅程

主导航保持现状：今日、随记、交易、案例、周复盘、随机复盘、仪表盘。

各模块职责收敛为：

- 今日：告诉用户今天最值得处理什么，并回放当前生效的周承诺；
- 随记：低成本捕捉未整理想法；
- 交易与错过机会：保存原始事实，触发复盘或提炼；
- 案例：把原始事实加工为可复习知识；
- 随机复盘：按到期计划重新暴露案例；
- 周复盘：从一周证据中只形成一条可执行承诺；
- 全局搜索：从任何工作区找回交易、案例、随记和周承诺。

目标旅程：

~~~mermaid
flowchart LR
    A["发现问题<br/>今日 / 平仓 / 错过 / 随记"] --> B["记录原始事实或提炼案例"]
    B --> C["来源证据只读保留<br/>案例洞见独立编辑"]
    C --> D["案例类型 + 掌握状态 + 错误标签"]
    D --> E["两条案例对比"]
    E --> F["带来源进入本周单一承诺"]
    F --> G["今日回放 / 全局检索 / 到期复习"]
    G --> A
~~~

这不是强制向导。用户可以在任一阶段停下，已保存内容仍独立成立；继续时，下一步入口在当前语境出现。

## 6. 跨阶段上下文

### 6.1 短暂上下文信封

发起动作通过现有路由 state 或工作区会话状态携带短暂上下文，不新增持久化“流程实例”：

~~~ts
interface ReviewFlowContext {
  origin:
    | 'today'
    | 'trade-close'
    | 'missed'
    | 'quick-note'
    | 'trade-detail'
    | 'case-list'
    | 'compare'
    | 'command-palette'
  sourceTradeId?: string
  sourceQuickNoteId?: string
  presetTradeKind?: 'live' | 'paper' | 'case'
  presetStatus?: 'missed'
  presetCaseType?: 'exemplar' | 'mistake' | 'ambiguous' | 'missed'
  compareRecordIds?: [string, string]
  returnContext?: ReviewReturnContext
}

interface ReviewReturnContext {
  pathname: string
  search: string
  savedViewId?: string
  anchorRecordId?: string
  scrollTop?: number
  focusKey?: string
  commandPalette?: {
    query: string
    activeResultKey?: string
    scrollTop: number
  }
}
~~~

它只负责连续操作，不写入导出快照。应用重启后若没有业务草稿，可安全退化到记录的规范详情地址；已经存在的编辑草稿继续由现有草稿机制恢复。

ReviewFlowContext 由当前主窗口的 workspace session 持有；其中 commandPalette 由顶层 CommandPalette 状态恢复，路由只传递不可变快照。关闭主窗口或通过主导航主动离开即丢弃，不能写入用户资料库或变成下次启动的隐性筛选。

### 6.2 继承优先级

新建或提炼时按以下顺序继承：

1. 明确来源记录；
2. 发起按钮显式传入的上下文；
3. 当前列表中唯一的结构化标的或策略筛选；
4. 现有创建器安全默认。

不继承自由搜索词、日期范围、排序、掌握状态或多选筛选。用户修改任何继承值后，以用户输入为准。

### 6.3 返回位置

从列表、搜索、今日或对比进入详情后，返回时恢复：

- 原路径和结构化筛选；
- 保存视图；
- 原锚点记录；
- 滚动位置；
- 最后触发控件的键盘焦点。

若锚点记录因操作不再满足筛选，恢复到原顺序中最近的仍可见记录，并说明“当前记录已移出此视图”。不把用户静默送回列表顶部。

## 7. 发现问题到记录案例

### 7.1 错过的机会

“错过的机会”是实盘、模拟盘和案例的聚合页，不应静默把所有新记录创建成案例。页面新增原地动作“记录错过”，不再要求先跳到别的模块。

表单固定保留 missed 状态，只询问一次必要来源：

- 实盘：创建 tradeKind=live、status=missed，进入周复盘执行缺口；
- 模拟：创建 tradeKind=paper、status=missed，不混入实盘统计；
- 案例：创建 tradeKind=case、status=missed、caseType=missed，作为独立知识记录。

若当前范围已经明确只有一种来源，自动继承并隐藏选择；若同时显示多种来源，使用紧凑的“实盘 / 模拟 / 案例”分段选择。保存后仍停留在错过机会工作区。

实盘或模拟错过记录保存成功后，反馈同时提供“提炼为案例”。从现有错过记录提炼时，自动继承标的、方向、策略、时段、周期、错误标签和来源复盘，caseType 固定为 missed，但用户在保存前仍可修正其他字段。

验收目标：

- 跨模块跳转 0 次；
- 已知字段重复录入 0 次；
- 必要来源选择不超过 1 次；
- 独立案例不会进入实盘周统计。

### 7.2 平仓

平仓成功反馈保留“撤销”，并增加“开始复盘”。“开始复盘”打开刚平仓交易详情并直接聚焦复盘正文；不自动完成复盘，也不自动创建案例。

如果正文尚未保存、图片仍在提交或平仓操作被撤销，“开始复盘”不得创建孤立状态。失败时停留原地并说明具体原因。

### 7.3 从交易提炼案例

“提炼为案例”在复盘完成反馈和来源附近提供可见次级动作；More 菜单仍可保留同一命令，但必须调用同一个实现。Cmd/Ctrl+K 在交易详情中也提供“提炼当前交易为案例”，不增加独立默认快捷键。

同一 sourceTradeId 已有关联案例时：

- 只有一条时，默认动作变为“打开已有案例”；
- 多条时，显示最近项优先的轻量选择；
- “另提炼一条”保留为显式次级动作；
- 双击、保存中重复触发或并发触发最多创建一条默认案例。

创建前先 flush 来源正文；保存失败时不创建案例。创建成功后来源事实只读展示，案例洞见为空白并获得焦点，避免把来源全文变成可二次编辑的案例正文。

### 7.4 从随记提炼案例

随记增加“提炼为案例”，但不把随记正文复制到可编辑案例正文，也不删除原随记。

发起提炼前先 flush 随记正文与图片草稿；flush 失败时停留原随记，不创建案例。

flush 成功后打开现有案例创建器的“来源随记”模式，不立即创建。由于随记本身没有交易结构，创建器不得沿用“做多、首个策略、今天、优秀范例”等静默猜测：

- tradeKind 固定为 case；
- symbol、side、strategyId、案例日期和 caseType 在创建前必须显式确认；
- 案例日期可预填随记 createdAt 对应业务日，并标明来源，其他字段只有存在显式 ReviewFlowContext 时才预填；
- 普通随记进入时，symbol、side、strategyId 和 caseType 为空，保存按钮保持不可用；
- caseType=missed 时新案例使用 status=missed，其他无交易结果的随记案例使用 status=planned；
- 取消创建只关闭创建器，不修改随记或生成来源引用。

首批增加一个最小可追溯字段：

~~~ts
interface Trade {
  sourceQuickNoteId?: string
}
~~~

现有 sourceNoteHtml 扩展为“来源记录正文快照”。来源交易和来源随记都在成功保存来源正文后单向同步所有关联案例；案例洞见从不反写来源。来源删除后，案例保留最后一次成功快照。

案例详情显示：

- 来源随记：只读；
- 案例洞见：独立、初始为空的可编辑正文；
- 原随记存在时提供“查看原随记”；
- 原随记删除后标记“来源已删除”，最后快照仍可读。

同源默认打开已有案例，多条时显示选择，并保留“另提炼一条”。图片继续引用现有资产 ID，不物理复制；只要案例快照仍引用资产，垃圾回收不得删除该资产。

## 8. 补充证据与案例详情

案例详情保持两个清晰层次：

1. 来源证据：只读，回答“当时发生了什么”；
2. 案例洞见：可编辑，回答“我从中学到了什么”。

来源交易和来源随记都遵守单向同步：

- 来源正文与所有关联案例快照在同一次 store transition 中更新，持久化成功后才反馈保存完成；
- 案例洞见不回写来源；
- 来源删除后保留最后一次成功快照。

独立创建的案例没有来源区，不显示空壳；证据直接通过现有富文本和图片能力添加。

证据加载要求：

- 加载中保留最终版式，不让正文和分类控件跳动；
- 单张资产失败只影响该槽位，显示稳定占位和重试；
- 来源缺失与资产缺失是两种不同状态；
- 来源同步失败不覆盖最后成功快照，并给出可重试反馈。

本批次不新增证据时间线、附件实体、OCR、图片批注或双向同步。

## 9. 分类与复习状态

### 9.1 案例的三条规范轴

案例生产界面只暴露：

- caseType：这是什么案例；
- masteryState：我现在掌握到什么程度；
- mistakeTags：问题具体发生在哪里。

三者职责互不替代：

- caseType 通常由用户判断，来源只提供默认值；唯一例外是明确执行“记录错过”或从 status=missed 来源提炼时，missed 是该流程的业务不变量；
- masteryState 由复习动作或用户显式修改；
- mistakeTags 不自动改写 caseType。

reviewCategory 只对案例降为兼容镜像，不再作为案例新建、编辑或常规筛选中的独立判断。实盘和模拟盘仍保留现有 reviewCategory 兼容语义。reviewStatus 对实盘和模拟盘继续表示“是否完成正文复盘”；对案例只保留兼容用途。

### 9.2 原子规范化

案例创建以及 caseType、masteryState、nextReviewAt 的分类相关 mutation 统一通过一个规范化边界。正文保存、来源同步、评论、图片和其他非分类 mutation 原样保留已有 reviewCategory/reviewStatus，不能因为普通保存洗掉 legacy focus。分类 mutation 的兼容镜像按下列顺序派生：

| 条件 | reviewCategory | reviewStatus |
| --- | --- | --- |
| masteryState=mastered | mastered | reviewed |
| masteryState=recheck | recheck | unreviewed |
| masteryState=new 且 caseType=mistake | mistake | unreviewed |
| masteryState=new 且 caseType=ambiguous | ambiguous | unreviewed |
| 其他新案例 | normal | unreviewed |

修改 caseType 时不改变 masteryState 或 nextReviewAt；修改 masteryState 时按复习规则更新 nextReviewAt；修改 mistakeTags 时不隐式改写类型或掌握状态。

legacy focus 案例首次发生分类 mutation 时，先在同一原子操作中加入 starredIds，再写规范兼容镜像；focus 快捷视图按“已星标或仍持有 legacy focus”匹配，因此不会因规范化丢失关注语义。新建 status=missed 案例必须同时为 caseType=missed；载入历史矛盾记录时先保持可读并显示修复提示，只有用户确认后才原子修正，不在普通正文保存时偷偷改写。

旧数据和导入仍可包含 reviewCategory=focus、reviewStatus=focus 等值：

- 继续支持读取、导入和旧保存视图；
- 不再产生新的 focus 兼容写入；
- 旧筛选被打开时显示“旧分类”筛选标签，允许移除；
- mistake、ambiguous、recheck、mastered 在可无歧义时分别映射到案例类型或掌握状态；
- normal 无法无损转换时继续按旧谓词读取；focus 的旧 URL 或保存视图由兼容适配器解释为“已星标或仍持有 legacy focus”，不再只做 reviewCategory 精确相等；
- 常规案例筛选面板不再并列显示三套重叠分类。

### 9.3 来源默认分类

从来源交易提炼时按以下规则给值，其中 missed 为业务不变量，其余为可修正默认：

1. status=missed → caseType=missed；
2. 明确模糊分类 → caseType=ambiguous；
3. 有错误标签或明确错误分类 → caseType=mistake；
4. 其他 → caseType=exemplar。

从错过页选择“案例”时 caseType 固定为 missed；从错误案例快捷视图创建时默认 caseType=mistake；普通案例页保持 exemplar 默认。若用户要记录非 missed 案例，应退出“记录错过”语境并使用普通案例创建；不能在同一表单里制造 status=missed、caseType 非 missed 的矛盾记录。掌握状态始终从 new 开始，不继承当前列表的掌握筛选。

## 10. 到期复习真相

nextReviewAt 必须真正控制默认随机复盘池。新轮次的默认时点为 due：

~~~ts
eligible =
  tradeKind === 'case' &&
  !deletedAt &&
  masteryState !== 'mastered' &&
  (nextReviewAt == null || nextReviewAt <= currentTradingDayKey)
~~~

规则：

- 缺少 nextReviewAt 的旧 new/recheck 案例视为今天到期，避免永久消失；
- mastered 无论残留什么日期都不进入默认池；
- “不熟悉”安排 3 天后并保持 new；
- “待复看”安排 7 天后并进入 recheck；
- “已掌握”清空日期并进入 mastered；
- 手工调整日期只改变日期，不改变案例类型；
- 日期使用当前业务交易日，在 Windows 与 macOS 同一时区配置下结果一致。

nextReviewAt 的规范写入格式固定为 YYYY-MM-DD。载入历史 ISO 时间戳时先按当前交易日起始小时转换为业务日；无效字符串与缺失日期对未掌握案例都按“今天到期”处理，并在下一次成功写入时规范为 YYYY-MM-DD，不允许形成永远无法命中的孤儿状态。

高级设置提供明确的“全部案例（含未到期与已掌握）”，作为用户主动覆盖。不得把上一次偶发的窄筛选永久记成下次默认。

ReviewSessionFilters 新增可选 reviewTiming：

~~~ts
type ReviewTiming = 'due' | 'all'
~~~

新会话默认 due；升级前已经进行中的会话缺少该字段时按 all 解释，保持原轮次成员不被升级静默删减。轮次结束后再次从默认入口开始使用 due。

高级选入实盘或模拟记录时，不显示“不熟悉 / 待复看 / 已掌握”。只提供“提炼为案例”和“下一条”；经过状态只记录在当前会话进度，不写 caseType、masteryState 或 nextReviewAt。

## 11. 连续复盘

### 11.1 完成并下一条

从待复盘列表或今日队列进入详情，且仍有下一条待复盘时，主要完成动作显示“完成并下一条”；没有有序上下文时仍显示“完成复盘”。

动作顺序：

1. flush 当前正文和图片草稿；
2. 用最新正文重新检查完成条件；
3. 记录本次 actionId 与完成前字段，原子写入复盘完成状态；
4. 等待附件操作结束，并 await flushPersistNow 的磁盘确认；
5. 确认落盘后，从原列表顺序找到下一条仍待复盘记录；
6. 导航并聚焦正文。

store 更新不等于完成。若磁盘写入失败，使用 actionId 只回滚本次修改的 reviewStatus/reviewedAt，不覆盖期间发生的正文或其他并发编辑，并再次尝试持久化回滚；回滚成功后停留原页并提供“重试完成”。若完成写入和回滚写入都失败，停留原页、显示“持久化状态待核对”的阻断错误并禁止自动跳转，不能用成功 Toast 掩盖不确定状态。

来源决定结束行为：

- 来自今日：队列清空后返回今日并聚焦对应队列；
- 来自筛选列表：最后一条完成后返回原列表锚点；
- 深链直接进入：完成后留在当前详情。

任一步失败都不得导航。用户可通过次级动作“仅完成”留在当前记录。

### 11.2 快捷键

首批只新增一个默认快捷键：

| 动作 | 默认键 | 范围 |
| --- | --- | --- |
| 完成并下一条 | Mod+Shift+Enter | 交易复盘详情 |

Mod 表示 Windows 的 Ctrl、macOS 的 Command。

编辑器内的 Mod+Enter 已由 TipTap 用于硬换行，因此不能分配给“完成”。“完成并下一条”在详情编辑器边界局部处理，但必须读取快捷键注册表中的当前绑定，不能在组件里再次硬编码 Mod+Shift+Enter；同时遵守 IME composition、重复按键、冲突检测和保存中禁用规则。

其他动作复用现有机制：

- 新建案例继续使用 Shift+N，并继承当前上下文；
- 提炼当前交易通过可见动作或 Cmd/Ctrl+K 当前记录命令；
- 两条对比先使用批量操作栏，不增加默认按键；
- 列表和详情统一 Q=上一条、E=下一条；
- 随机复盘现有 1/2/3、N/P 进入可配置注册表，默认键不变。

## 12. 两条案例对比

### 12.1 入口与边界

第一版只比较案例，不比较任意账户交易，不创建持久化对比实体。

- 复用案例列表现有批量操作栏；
- 恰好选中两条时显示“对比”；
- 少于或多于两条时禁用并说明“请选择 2 条案例”；
- 不增加“同类案例推荐”，由用户现有筛选、保存视图和搜索决定比较对象；
- 不使用 AI 相似性或自动结论。

### 12.2 工作区内对比层

对比使用工作区内 Sheet，不新增路由。支持桌面窗口下限 960×640：

- 工作区宽度不小于 1280 时左右双列；
- 960–1279 时按章节显示 A/B 上下分段，避免窄列和横向滚动；
- 标题与关闭按钮固定在顶部，后续动作固定在底部；
- 两条案例始终是上限。

Sheet 打开期间背景工作区设为 inert 并从辅助技术浏览顺序隐藏，焦点锁定在 Sheet 内，初始焦点落在可见关闭按钮；Tab/Shift+Tab 不逃逸，Escape 关闭后回到批量操作栏“对比”。

两侧按相同章节对齐：

1. 编号、标的、方向、策略、周期、日期与结果或错过原因；
2. 案例类型、掌握状态、错误标签；
3. 来源记录与来源证据；
4. 案例洞见。

相同结构化值弱化，差异值强调；不生成“AI 结论”。长正文允许章节内展开，主层只有一个滚动位置。

证据加载与失败：

- 两侧并行加载，各自显示稳定骨架；
- 一侧失败不阻塞另一侧；
- 图片失败保留槽位并可重试；
- 来源已删除时显示保留快照；
- 单侧字段为空显示“未记录”，不塌缩对齐结构；
- 任何失败都不关闭对比或清空选择。

### 12.3 退出与后续动作

Escape、关闭按钮或返回动作关闭对比后，恢复两条选择、列表滚动和“对比”按钮焦点。

底部只有一个知识后续动作：“带这两条进入周复盘”。它携带两条案例 ID 打开本周周复盘并聚焦现有承诺区，不自动生成规则文字，不在对比层复制编辑器。

从周复盘执行返回时，若两条案例仍存在，则恢复原列表和同一对比层；若其中一条已删除，则恢复列表并说明无法重开对比。通过主导航主动离开不强制恢复对比。

## 13. 规则沉淀与回放

### 13.1 只有完成的单一承诺才是规则

现有周复盘已经包含：

- commitmentText；
- commitmentCriteria；
- previousCommitmentResult。

产品约束是“下周只改变一件事”。因此不新增 ruleCandidates 数组、规则状态机或顶级规则实体。对比中的内容只作为短暂来源上下文，用户最终保存的仍是本周唯一承诺。

### 13.2 最小来源关联

WeeklyReview 只增加一个可选来源数组：

~~~ts
interface WeeklyReview {
  commitmentSourceRecordIds?: string[]
}
~~~

从对比进入周复盘时，两条来源先进入页面内存草稿，不立即写持久化：

目标固定为当前业务交易周。该周尚无 WeeklyReview 时只构造现有的内存默认草稿，直到用户首次实际修改或显式确认来源才创建持久化记录。

- 承诺为空：显示两条待带入来源并聚焦承诺文字；
- 已有承诺：不覆盖文字，显示“将追加为现有承诺来源”；
- 用户取消或直接返回：不写来源关系；
- 用户首次实际修改承诺或验收条件时，来源与该次自动保存使用同一个原子 patch；
- 若文字无需修改，用户可显式选择“确认加入来源”；
- 周复盘已完成：不修改冻结数据，只读打开并说明必须显式重新打开才能调整。

若用户在该只读页显式执行现有“重新打开”，两条待带入来源继续保留在本窗口内存并转入可编辑草稿；取消重新打开、返回或主导航离开则丢弃待带入来源，不写任何关系。

首版 commitmentSourceRecordIds 只接受 case 记录 ID。重复从另一组对比进入时使用“已有顺序 + 新对比左侧 + 新对比右侧”稳定追加并去重，不替换已有来源；用户可以在草稿中逐条移除。完成周复盘时，承诺文字、验收条件和来源 ID 与现有指标、证据和风险快照一起冻结。已删除来源显示“来源已删除”，不静默替换。

### 13.3 今日回放

周 W 完成的承诺只在紧接着的 W+1 生效。今日页只显示“上一周已完成且当前周生效”的承诺：

- 一行承诺；
- 一行验收条件；
- 来源数量；
- “查看来源周复盘”。

草稿、未来周和更早的陈旧承诺不显示为当前规则。卡片不占用风险预检主按钮，不弹窗，不要求每天确认。历史承诺通过全局搜索找回。

周承诺和版本化风险纪律保持独立。本批不提供自动覆盖或“带入风险纪律”动作。

## 14. 全局检索与复用

继续使用 Cmd/Ctrl+K，不新增搜索页面或远端索引。

### 14.1 搜索语料

结果按类型分组并明确标识：

- 案例：编号、标的、策略、普通标签、错误标签、案例类型、掌握状态、案例洞见、来源证据；
- 交易：编号、标的、策略、普通标签、错误标签、复盘正文、评论；
- 随记：标题、正文；
- 周承诺：仅已完成周复盘的承诺、验收条件和来源编号；
- 现有命令、策略、标签和保存视图继续保留。

草稿周承诺不作为“规则”进入结果。富文本在本地去标签、解码实体后索引；每个正文域最多索引前 4,000 个纯文本字符。图片二进制、OCR 内容和未保存草稿不进入索引。

### 14.2 排序、组间配额和反馈

组内排序固定：

1. 编号或标的精确匹配；
2. 标题、策略、标签精确匹配；
3. 前缀匹配；
4. 正文子串匹配；
5. 同分时按最近业务更新时间。

最近业务更新时间的回退固定为：交易或案例取 activities 最新 timestamp、reviewedAt、recordedAt、closedAt、openedAt 中的最大有效值；随记取 updatedAt；周承诺取 completedAt，其次 updatedAt。仍同分时按 ref、标题或 ID 做稳定字典序，避免结果每次打开抖动。

最多显示 24 条知识结果，每组最多 8 条；只要某组有匹配，至少保留 1 个结果位，不能让大量交易结果挤掉随记或周承诺。

结果显示类型、主要标题、命中字段和短摘要。案例不能再统一标成“交易”；周承诺显示所属周。打开结果后返回命令面板时恢复查询、活动项、滚动和输入焦点。

索引只对变更实体增量更新，不在每次按键重建整个语料。20,000 条混合记录基准：

- 热查询输入到结果更新 p95 不超过 100 ms；
- 命令面板打开到可输入 p95 不超过 200 ms；
- 连续输入不丢键、不冻结编辑器。

若任一双平台基线仍不能达标，再把查询移入本地 Worker；第一版不预先引入搜索服务、数据库或模糊语义引擎。

### 14.3 可复现性能协议

PERF-01 使用固定种子 atlas-search-20000-v1 生成 20,000 条：10,000 条实盘、2,000 条模拟盘、6,000 条案例、1,800 条随记、200 条已完成周复盘。富文本纯文本长度分布固定为 70%×600 字符、25%×2,000 字符、5%×4,000 字符；每条交易或案例包含 3 个普通标签，案例包含 1 个错误标签，周复盘均有承诺与验收条件。

固定查询集覆盖 9 类：精确编号、精确标的、策略、错误标签、案例正文唯一词、来源正文唯一词、随记唯一词、完成承诺唯一词、匹配超过 60 条的公共词；另记录一次无结果查询，但不纳入有结果排序正确率。

测量协议：

1. 使用打包 production Electron，关闭 DevTools，缩放 100%，资料库位于本地 SSD；
2. 等待存储 hydrated 和搜索索引 ready，完整查询集预热 2 轮；
3. 查询集按固定伪随机顺序运行 50 轮，共 450 个有结果样本；
4. 查询延迟从输入事件进入 CommandPalette 到结果 DOM 提交后的首个 requestAnimationFrame，且 aria-busy=false；
5. 面板打开延迟从快捷键事件进入主窗口到搜索输入获得焦点，预热 5 次后测量 50 次；
6. 分别报告每类查询和总体 p50/p95/max，不用平均值代替 p95；
7. Windows 基线为 Windows 11 x64、Intel Core i5-1135G7、16 GB、NVMe；macOS 基线为 macOS 15、Apple M1 8 核 CPU、16 GB；使用该配置或更慢的已记录参考机，两端均记录实际 CPU、内存、Electron 版本、构建 hash 和电源模式。

100 ms 查询和 200 ms 打开门槛必须在两端分别满足；一端失败即 PERF-01 失败。

## 15. 反馈、焦点与错误边界

### 15.1 即时反馈

- 继承上下文后用一行弱提示说明来源，不逐字段弹 Toast；
- 同源已有案例时直接显示“打开已有案例”，不等保存后才报重复；
- 完成、提炼、带入规则和删除均说明作用对象；
- 保存中禁用重复提交，但不锁住阅读和取消；
- 成功 Toast 只提供真正有用的后续动作。

### 15.2 焦点

- 表单、Sheet 和命令面板打开后焦点进入首个业务控件；
- 关闭后回到触发控件；
- 完成并下一条后进入新记录正文；
- IME 组合输入期间任何单键或组合键都不触发工作区动作。

### 15.3 错误

- 正文或图片 flush 失败：停留原记录，完成状态不变；
- 来源在操作中被删除：若有快照则继续并标记来源缺失，否则取消并说明；
- 同源并发提炼：存储层再次检查，默认只生成一条；
- 对比期间记录被删除：保留另一侧，缺失侧显示状态并禁止带入规则；
- 周复盘已冻结：绝不隐式重新打开；
- 搜索结果对应记录已删除：移除该结果并保留查询。

所有失败路径要求 0 条静默数据写入、0 次错误导航。

## 16. 数据兼容与迁移

本设计新增两条持久化引用：

- Trade.sourceQuickNoteId；
- WeeklyReview.commitmentSourceRecordIds。

来源不变量：只有案例可以持有来源引用；sourceTradeId 与 sourceQuickNoteId 互斥；独立案例两者都没有；sourceNoteHtml 是最后成功来源快照，即使来源后来缺失也可以继续存在。导入数据同时提供两种来源时直接拒绝并说明，不静默选择其中一种。

实现时 schema 从 11 升至 12，并完成：

1. 旧快照缺少 sourceQuickNoteId 时保持 undefined；
2. 旧周复盘缺少 commitmentSourceRecordIds 时运行时规范为 []；
3. snapshotValidation 校验可选字符串和去重字符串数组；
4. 导入冲突时重写 commitmentSourceRecordIds 中的案例 ID；目标仍存在时必须验证 tradeKind=case，目标已经彻底缺失时保留悬空 ID 供界面显示“来源已删除”；
5. 为随记建立稳定导入 ID 映射，并重写 sourceQuickNoteId，避免碰撞后指向本地另一条随记；
6. snapshot codec、导出、导入、并发合并和完整 fixture 验证引用往返；
7. sourceNoteHtml 继续参与图片外置、资产盘点、归档和垃圾回收；
8. 删除来源随记不级联删除案例或来源快照。

reviewCategory、reviewStatus 和旧保存视图字段本批不删除，避免破坏历史归档。案例界面停止新增独立写入，查询层继续兼容。

ReviewSessionFilters.reviewTiming 属于会话快照兼容字段；旧会话缺失时按 all，新会话明确写 due。

### 16.1 Electron 资料库迁移协议

当前 electron/library/schemaMigration.ts 的 marker、恢复目录、候选数据库、fromVersion 联合类型、校验分支和错误文案仍编码 v8/v9/v10。schema 升到 12 前必须先把这条协议泛化，不能只修改 SCHEMA_VERSION：

- fromVersion 至少接受 8、9、10、11，并把当前 v11 资料库作为主要升级路径；
- 新 marker、恢复目录和候选数据库名称不再写死 v8-to-v9，恢复结果和错误文案也使用实际 fromVersion/toVersion；
- 仍识别并安全完成旧客户端留下的 v8-to-v9 marker，不能因重命名让中断恢复失联；
- 迁移前复制 journal.db 与 manifest.json，校验 checksum，并重新打开副本验证 snapshot；
- 候选数据库、正式数据库和 manifest 必须在 prepared、database-replaced、manifest-replaced 三个阶段都可判定恢复或继续；
- 清理候选文件或恢复目录中断后，下一次启动仍能幂等完成；
- v11→v12 在每个阶段加入强制终止和 I/O 失败测试，验证不会得到数据库版本、manifest 版本不一致的资料库；
- 运行时重新打开正式数据库与 manifest pair，并通过 canonical snapshot 和引用校验后，才删除恢复副本；重新启动、导出、导入属于发布验收，不作为等待用户操作的运行时删除条件。

格式版本边界固定为：普通 JSON 的 EXPORT_VERSION 随 SCHEMA_VERSION 升至 12；Web Journal ZIP 容器结构没有变化，因此 WEB_JOURNAL_EXPORT_VERSION 保持 9，桌面 .journal.zip 容器 marker 仍保持 1，但两者内嵌 schemaVersion 写 12。必须增加“旧容器 + schema 11 导入”和“同容器 + schema 12 往返”测试，不能把容器版本与数据 schema 混为一谈。

## 17. 分批实施顺序

### 批次 0：状态真相

- 统一案例分类写入；
- 默认随机池按到期时间；
- 非案例不写掌握字段且不显示掌握评分；
- 统一 Q/E，注册随机复盘现有快捷键；
- 补齐旧会话和旧筛选兼容测试。

这批先消除“界面说一件事、数据做另一件事”，不依赖新界面。

### 批次 1：前段上下文连续性

- 错过页原地记录与一次来源选择；
- 平仓后开始复盘；
- 显式上下文继承；
- 同源默认幂等和“另提炼一条”；
- 随记可追溯提炼与来源同步；
- 完成并下一条、返回锚点和唯一新增默认快捷键。

### 批次 2：对比到单一承诺

- 两条案例对比层；
- 证据加载和焦点恢复；
- commitmentSourceRecordIds；
- 从对比进入周承诺；
- 今日回放当前生效承诺。

### 批次 3：检索复用

- 本地分组索引与组间配额；
- 命中字段、来源和返回状态；
- 20,000 条性能基准；
- Windows/macOS 命令键与键盘验收。

每批都可以独立验收和发布，后一批不得用“先建复杂基础设施”为前提。批次 1 在写入 schema 12 前必须生成可恢复备份，并一次性包含两条可选引用的 codec 与校验能力；数据已经写成 schema 12 后，不把降级到只理解 schema 11 的客户端描述为安全回滚。

### 19.3 Electron 正式验收

1. 真实应用菜单与 Mod 映射；
2. 原生目录选择和持久化资料库；
3. 图片资产保存、同步、删除与重启恢复；

## 20. 明确非目标

- 不新增顶级导航、规则中心、对比项目或知识图谱；
- 不建立多条规则候选及其生命周期；
- 不用 AI 自动推荐相似案例、生成对比结论或交易规则；
- 不新增证据时间线、OCR、图片批注或远端搜索服务；
- 不联动或自动覆盖版本化风险纪律；
- 不在随机复盘逐条追问规则是否适用；
- 不把偶发随机复盘筛选记成全局默认；
- 不重写现有交易、周复盘或来源同步架构；
- 不为手机、iPad、浏览器或其他平台做产品适配；
- 不以删除旧字段的方式强迫一次性迁移历史数据。

## 21. 方案取舍

未采用“只补几个按钮”，因为它能缩短前两步，却无法解释分类、复习计划、规则来源和检索，后半段仍然断裂。

未采用“独立知识系统”，因为规则库、关系图、自动推荐和证据实体会引入新的生命周期与维护负担，让高频用户重新学习软件。

方案 B 内部进一步收敛：

- 原设想的 ruleCandidates 数组被取消，改为现有单一承诺加来源 ID；
- 错过页不强行一击创建案例，只保留一次不可替代的来源判断；
- 删除“同类案例推荐”、风险纪律联动和逐条规则追问；
- 四个新默认快捷键收敛为一个高频“完成并下一条”。

这些取舍减少了表面上的“功能完整感”，换来更真实的数据、更少的状态和更低的长期认知负担。

## 22. 完成定义

本设计只有在以下条件同时满足时才算实现完成：

1. 验收矩阵 27 项都有自动化或 Windows/macOS 实机证据；
2. 七段旅程能从任一发现入口连续完成，不需要用户猜模块；
3. 默认复习池与持久化状态一致；
4. 同源、保存失败、来源删除和导入冲突不会制造静默数据错误；
5. 连续 20 条高频复盘不丢上下文、不丢焦点、不丢草稿；
6. 对比产生的来源能进入唯一周承诺，并在适用周被看到和检索；
7. 没有为闭环新增顶级模块、规则候选库或非桌面平台分支。
