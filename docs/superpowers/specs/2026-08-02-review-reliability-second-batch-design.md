# 复盘可靠性第二批优化设计

日期：2026-08-02  
状态：已确认设计，待实施计划  
范围：历史周补做入口、风险数据缺口诊断与修复导航

## 目标

在不改变产品定位、不新增持久化实体的前提下，解决两个长期使用中的可靠性断点：

1. 用户跳过某周后，即使该周存在交易活动，也无法首次补做周复盘。
2. 风险状态提示“未知”或“部分覆盖”时，用户看不到具体受影响交易与修复方向。

成功标准：用户能从周复盘直接进入最近活动周补做复盘；能在风险设置页看到当前风险周期内全部数据缺口，进入对应交易修复，并在返回后看到问题自动消失。

## 设计原则

- 单一事实来源：活动周与风险缺口都从现有交易、交易日配置和风险规则实时推导。
- 不制造同步债务：不保存“待补做周”或“待修复任务”，不增加 schema 字段。
- 不改写历史：已完成周复盘继续展示冻结指标与证据。
- 修复导向：风险提示必须落到具体交易或明确的全局配置入口。
- 范围克制：本批不重做周复盘布局，不增加任务管理系统，不改风险计算含义。

## 方案选择

采用共享纯函数推导方案。

未采用页面独立计算，因为它会复制交易日、结果可信度和风险规则判断，容易再次产生跨页面口径分裂。未采用持久化修复任务，因为任务失效、同步和迁移成本超出本批目标。

## 架构设计

### 活动周推导

新增独立纯函数，根据以下输入生成可选周列表：

- 当前交易周；
- 已有周复盘的 `weekStart`；
- 未删除实盘中，按现有周复盘事实口径归属的已平仓交易与错过机会；
- `tradingDayStartHour`。

输出规则：

1. 当前周始终保留。
2. 所有已有周复盘永久保留，不受数量上限影响。
3. 从交易活动中补入最近 12 个活动周。
4. 仅有计划、持仓、模拟盘、案例或删除记录的周不算活动周。
5. 周键去重后按新到旧稳定排序。

活动周应复用 `tradesClosedInWeek`、`missedTradesInWeek` 所依赖的交易日事实，或提取与二者共享的周键函数，避免另写自然日筛选。

### 风险逐笔诊断

在现有风险预算计算内部提取共享的逐笔评估结果。每笔结果至少包含：

- `tradeId`；
- 风险核算交易日；
- 是否能生成可信预算 R；
- 阻断原因；
- 部分覆盖原因。

风险汇总继续从同一逐笔结果生成，保持现有日、周、月数值和覆盖状态不变。风险设置页通过公开的纯函数取得诊断清单，不自行复制计算规则。

诊断项分为：

- `blocking`：无法安全判断风险状态；
- `partial`：不阻断开仓判断，但导致覆盖不完整；
- `global`：风险核算起点等不属于单笔交易的问题。

同一交易的多个原因合并为一个诊断项。诊断清单按 `blocking`、`partial`、交易日、交易编号稳定排序。

## 页面交互

### 周复盘历史

- 历史栏显示当前周、已有周复盘和最近 12 个活动周。
- 活动周尚无实体时显示“待补做”。
- 选择“待补做”周只切换查看范围，不创建空周复盘。
- 用户首次编辑正文、评分、选择证据或填写承诺时，沿用现有延迟创建逻辑生成周复盘。
- 上一周、下一周按钮使用相同的可选周序列。
- 已完成历史周仍读取冻结快照，不因当前交易变化而改写。

### 风险待修复数据

在风险设置页的规则表单之前增加“待修复数据”区：

- 摘要显示“阻断风险判断 N 条”和“影响完整度 N 条”。
- 阻断项优先展示，部分覆盖项随后展示。
- 每行展示交易编号、标的、问题原因、影响级别与“打开交易”。
- 详情导航携带 `/settings/risk` 来源状态，返回时回到风险设置页。
- Zustand 中的交易或规则变化会触发重新推导；问题修复后自动消失。
- 无问题时显示紧凑成功状态“当前风险周期数据完整”。
- 全局核算起点问题不伪装成交易项，提供“调整核算起点”入口并跳转数据设置。

## 原因与行动文案

现有阻断原因继续复用统一展示文案：

- `missing-loss-pnl`：亏损交易缺少盈亏金额；
- `result-conflict`：交易结果口径冲突；
- `missing-policy`：该平仓日没有生效的风险规则；
- `missing-close-date`：亏损交易缺少平仓日期；
- `invalid-close-date`：平仓日期无效；
- `future-loss-close-date`：亏损平仓日期晚于当前交易日；
- `invalid-live-cycle-start`：风险核算起点晚于当前交易日。

部分覆盖原因需显式建模，至少区分非亏损记录的结果金额不完整、平仓日期不完整、未来平仓日期与缺少可用风险规则。文案应说明它们影响覆盖完整度，但不把它们描述成已经确认的亏损风险。

## 错误与边界处理

- 只诊断当前风险周期内、未删除、已平仓的实盘交易。
- 模拟盘、案例、计划、持仓和风险周期之前的交易不进入清单。
- 旧数据日期异常只产生诊断项，不让设置页崩溃。
- 缺历史风险规则通常无法只靠编辑交易解决；文案明确边界，仍允许查看交易事实。
- 全局核算起点异常单独显示，并提供正确的设置入口。
- 诊断函数不得修改交易、规则或 Store。
- 风险计算重构前后必须保持相同的数值、覆盖状态、触发状态和原因顺序。

## 测试策略

### 活动周单元测试

- 当前周始终存在；
- 最近 12 个活动周上限；
- 所有已有周复盘永久保留；
- 空周不出现；
- 已平仓实盘与错过机会形成活动周；
- 模拟盘、案例、未结束和删除记录被排除；
- 凌晨交易按 `tradingDayStartHour` 归属正确周次；
- 输出去重且按新到旧排序。

### 风险诊断单元测试

- 亏损缺金额；
- 结果口径冲突；
- 缺失、无效及未来平仓日；
- 缺历史风险规则；
- 非亏损交易造成的各类部分覆盖；
- 风险核算起点异常；
- 同一交易多原因合并；
- 当前风险周期、删除和交易类型边界；
- 诊断稳定排序；
- 重构前后的日、周、月风险结果保持现有测试契约。

### 浏览器测试

- 活动周显示“待补做”，进入时不创建实体，首次编辑后才创建；
- 上一周、下一周能遍历推导后的周列表；
- 风险页显示数量、级别和原因；
- “打开交易”携带风险设置返回上下文；
- 修复 Store 中的交易后，对应问题自动消失；
- 全局核算起点问题跳转数据设置；
- 无问题时显示紧凑完整状态。

### 完成门禁

- `pnpm typecheck`；
- 受影响目标测试红绿循环；
- `pnpm test` 完整套件；
- 风险管理移动端 QA；
- `git diff --check`；
- UTF-8 严格解码、无 BOM 与治理检查。

## 非目标

- 不新增风险任务状态、负责人、截止时间或手动完成按钮。
- 不允许在风险页内直接编辑交易。
- 不重新定义净风险预算、风险规则版本或月度冻结逻辑。
- 不扩展到 Today 历史债务、随记归档、日期选择器或详情布局。
- 不自动创建 12 个周复盘实体。
