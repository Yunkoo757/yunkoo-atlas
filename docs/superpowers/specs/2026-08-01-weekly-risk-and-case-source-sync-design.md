# 周复盘风控重设计与案例来源正文持续同步设计

## 1. 背景

当前周复盘的“风控执行”同时平铺规则版本、每日结果、本周结果、月度结果和继续交易确认。所有数据使用近似等权的卡格表达，导致以下问题：

- 用户无法第一眼确认本周是否触线、还剩多少风险空间；
- 每日结果、本周最终和完成时月度被放进同一网格，周期层级不清；
- 规则 ID 与纪律文本常驻展开，审计信息压过决策信息；
- 空白补位格、重复的覆盖与上限文案制造无效视觉重量；
- 样式未充分复用现有表面、间距、字号和语义色 token。

案例正文目前只在“提炼为案例”时复制一次。详情编辑器使用延迟草稿提交，用户刚补充正文后立即提炼时，案例可能读取 store 中的旧正文；案例创建后，原交易后续补充的复盘信息也不会进入关联案例。

## 2. 目标

1. 周复盘风控区首先回答“本周是否触线、剩余多少 R、完成时月度状态如何”。
2. 每日风险结果形成可扫描轨迹，不再使用等权统计方格。
3. 规则版本和继续交易确认降为可展开的冻结审计证据。
4. 风控模块严格消费项目现有设计 token，不新增页面私有颜色、字号、间距、圆角或阴影值。
5. 原交易正文保存后，持续单向同步到所有关联案例。
6. 案例自己的沉淀正文始终独立可编辑，自动同步不得覆盖用户内容。
7. 创建案例前强制提交来源交易正文草稿，避免复制旧正文。
8. 原交易删除后，案例仍保留最后一次成功同步的来源正文快照。

## 3. 非目标

- 不改变风险预算、覆盖状态、触线判断或周复盘冻结口径。
- 不新增风险预测、日内高点回撤或自定义预警阈值。
- 不同步原交易的标签、策略、盈亏、分类、评论或活动记录。
- 不允许案例正文反向写回原交易。
- 不自动拆分或删除历史案例中的已有正文。
- 不重设计周复盘其他模块。

## 4. 周复盘风控信息架构

### 4.1 区块头部

保留“R / 风控执行”和“完成时冻结证据”的现有语义，但压缩为单行区块头：

- 左侧：`R` 标识与“风控执行”；
- 右侧：只读状态“完成时冻结”；
- 不在头部重复说明规则、周期或覆盖口径。

### 4.2 双周期决策带

风控区第一层只放两个结论：

1. **本周风险状态**：主位，显示是否触线、剩余 R、实际消耗与周限制；
2. **完成时月度状态**：次位，显示剩余 R、实际消耗与月度限制。

状态文案直接来自现有事实，不增加新的业务阈值：

- `triggered === true`：`已触线`；
- `coverage === 'unknown'`：`无法确认`；
- `coverage === 'partial'`：`部分覆盖`；
- 其他：`未触线`。

每个周期显示一条短进度轨迹，使用现有 `progress`、`consumedR`、`remainingR` 与 `limitR`。轨迹是辅助扫描，不替代精确数值。

### 4.3 每日风险轨迹

每日 outcome 改为纵向列表，每行固定三个信息位：

- 日期；
- 当日最终 budget R；
- 覆盖状态。

按 snapshot 中的日期顺序展示，不补空白格，不重复显示每行相同的“上限”说明。覆盖提示仅在 `partial` 或 `unknown` 时追加原因摘要；完整状态只显示“完整”。

### 4.4 冻结审计层

规则版本和继续交易确认放在每日轨迹之后：

- **规则版本**默认显示摘要：版本数量与首末生效日期；展开后显示生效日期、纪律文本和完整 ID；
- **继续交易确认**无事件时显示单行“本周无”；有事件时显示数量，并可展开原因、冻结交易身份、关联状态和交易链接；
- 现有完成时冻结数据保持只读，不从实时风险状态回算。

原生 `details/summary` 优先用于展开行为，键盘、读屏和无脚本场景均可使用。

## 5. 视觉与 token 约束

风控模块只消费以下现有 token 角色：

- 表面：`--bg-surface`、`--bg-elevated`、`--bg-inset`；
- 边框：`--border-subtle`、`--border-default`、`--border-strong`；
- 文字：`--text-strong`、`--text-body`、`--text-muted`、`--text-faint`；
- 状态：`--neg`、`--warn`、`--pos`、`--accent`；
- 间距：`--sp-1` 至 `--sp-8`；
- 圆角：`--radius-6`、`--radius-8`、`--radius-10`；
- 字体角色：`--type-section-title-*`、`--type-body-size`、`--type-metadata-*`；
- 数据字体：`--font-mono`。

约束：

- CSS 不写十六进制、LCH、RGB 等页面私有颜色；
- 不写新的固定字号、间距、圆角或阴影值；
- 本周结论是唯一高权重数据；每日行和审计证据保持安静；
- 颜色必须与文字状态同时出现，不使用纯颜色编码；
- 数值使用 tabular/mono 排版，文本继续使用 UI 字体；
- 不嵌套装饰性卡片，不用阴影区分普通数据层级。

### 5.1 响应式

- 宽屏：双周期决策带为两列，每日轨迹保持单列；
- 窄屏：双周期结论纵向堆叠，日期、数值和覆盖状态仍在单行内；
- 所有展开入口和交互命中区遵循现有触屏 token；
- 不产生横向滚动，不缩小正文到项目 token 以下。

## 6. 案例正文双区模型

案例详情将正文分成两个语义区域。

### 6.1 来源复盘

- 只读；
- 展示原交易最近一次成功保存的正文；
- 原交易存在时继续显示来源交易入口；
- 原交易删除或最终清理后，继续显示最后一次同步快照；
- 图片和附件使用现有正文解析与缺失资源恢复逻辑。

### 6.2 案例沉淀

- 独立可编辑；
- 用于规律、结论、模板化总结和后续学习记录；
- 保存只更新案例自己的 `note`；
- 永不反向更新来源交易，也不被来源同步覆盖。

## 7. 数据模型

在 `Trade` 的案例字段中增加可选字段：

```ts
/** 关联来源交易最近一次成功保存的正文快照；仅案例记录使用。 */
sourceNoteHtml?: string
```

字段保持可选，旧资料库可以直接加载。新建案例必须写入该字段，案例自己的 `note` 初始为空。

快照 codec、校验、导入导出和 Electron/Web 持久化路径必须保留该字段。正文附件引用收集、孤立附件预览、清理保护和恢复归档必须同时扫描 `trade.note` 与 `trade.sourceNoteHtml`，避免来源删除后误清理案例快照仍引用的资源。

## 8. 同步数据流

### 8.1 创建案例

详情页触发“提炼为案例”时：

1. 阻止重复提交；
2. 调用 `flushNoteDraftToStore(sourceId)`；
3. 若提交失败，终止创建并提示“正文尚未保存，未创建案例”；
4. 从 `useStore.getState()` 重新读取来源交易，禁止使用 render 闭包中的旧对象；
5. 创建案例：`sourceNoteHtml = latestSource.note`、`note = ''`；
6. 写入案例后再导航到案例详情。

列表和看板入口没有活动详情编辑器，但同样必须通过统一的 store 创建动作 `createReviewCaseFromTrade(sourceId)`，从当前 state 读取来源交易，避免三个入口继续复制不同逻辑。该动作只接受来源 ID，并返回“已创建 + 案例 ID”或“来源不存在 / 来源已经是案例”的显式结果；页面不再自行拼装案例字段。详情页负责在调用该动作前提交草稿，store 动作负责在执行瞬间再次读取最新来源。

### 8.2 来源正文保存

`updateNote(sourceId, html)` 在同一个 store 事务中：

1. 更新来源交易 `note` 与来源交易的正文活动记录；
2. 找出所有 `tradeKind === 'case' && sourceTradeId === sourceId` 的关联案例，包括软删除但仍可恢复的案例；
3. 只更新关联案例的 `sourceNoteHtml`；
4. 不修改案例 `note`、标签、掌握状态、评论、活动记录或更新时间语义。

来源图片归一化成功后才进入 `updateNote`，因此案例只接收可持久化的最终 HTML。同步不单独创建案例活动，避免派生快照污染案例时间线。

### 8.3 案例正文保存

案例 `updateNote(caseId, html)` 只更新案例 `note`。因为 `tradeKind === 'case'`，不得触发来源同步或其他案例级联。

### 8.4 删除与恢复

- 来源交易软删除或最终清理不清空案例 `sourceNoteHtml`；
- 来源存在时，案例的“查看原交易”入口正常可用；
- 来源不存在时显示“原交易已不存在”，来源复盘快照仍可读；
- 案例删除和恢复不影响来源交易；软删除期间仍接收来源正文快照，恢复时直接展示最新版本。

## 9. 历史兼容

历史案例没有 `sourceNoteHtml`，且其 `note` 可能同时包含系统复制的来源正文和用户后续编辑内容。由于无法可靠区分两者：

- 不自动清空、裁剪或重写历史案例 `note`；
- 来源交易仍存在时，读取其最新正文作为“来源复盘”，并在下一次来源保存时写入 `sourceNoteHtml`；
- 来源已不存在时，`sourceNoteHtml` 缺失则显示历史案例正文，不伪造来源快照；
- 只有正文与系统生成副本能够严格逐字匹配时，后续迁移才可以无损归位；本次不引入启发式拆分。

该策略可能让少量历史案例同时出现旧副本和最新来源区，但优先保证零数据丢失。

## 10. 错误与状态反馈

- 草稿提交失败：不创建案例，保留用户草稿与当前页面；
- 来源正文附件归一化失败：保持上一版来源与案例快照，不写半成品；
- 同步为内存事务，不显示每次自动同步 toast；现有保存状态继续表达持久化进度；
- 案例来源缺失：显示明确状态，不隐藏最后快照；
- 来源快照附件缺失：复用正文只读恢复提示，不让编辑器错误地进入可编辑状态。

## 11. 组件与职责

- `WeeklyReviewView`：编排双周期决策带、每日轨迹和审计层；
- `WeeklyReviewView.css`：只实现风控区结构和响应式，全部视觉值来自 token；
- `reviewCases`：构造来源快照与独立案例正文；
- `useStore`：统一创建案例、来源正文级联和案例正文隔离；
- `DetailView`：创建前提交草稿，展示只读来源复盘与可编辑案例沉淀；
- snapshot codec/validation/asset lifecycle：保留新字段并保护其附件引用。

每个单元只承担一种职责，页面组件不自行遍历并修改关联案例。

## 12. 测试设计

### 12.1 风控呈现

- 本周结论在每日轨迹和审计信息之前；
- 本周与月度显示精确结果、限制、剩余和覆盖状态；
- 每日 outcome 数量与顺序和 snapshot 一致，无空白补位；
- 规则和继续交易确认默认摘要、可键盘展开；
- `complete`、`partial`、`unknown`、`triggered` 均显示文字状态；
- 375、768、1280、1920 宽度无裁切、重叠和横向滚动；
- 计算样式验证颜色、间距、字号、圆角和字体来自项目 token。

### 12.2 案例同步

- 创建案例读取提交后的最新来源正文；
- 草稿提交失败时不创建案例；
- 来源 `updateNote` 同步所有关联案例的 `sourceNoteHtml`；
- 来源同步不改变案例 `note`、活动、分类和掌握状态；
- 案例正文更新不改变来源或其他案例；
- 来源删除后案例快照仍可显示；
- 历史案例正文不会在规范化或同步时被清空；
- codec、验证、导入导出保留 `sourceNoteHtml`；
- 附件生命周期把 `sourceNoteHtml` 中的资源计为有效引用；
- 浏览器集成覆盖“编辑来源正文后立即提炼”和“创建后继续编辑来源正文”两条真实路径。

## 13. 验收标准

1. 风控区第一眼可以看到本周是否触线、剩余 R 与完成时月度状态。
2. 每日结果不再显示为等权大方格，也没有空白补位格。
3. 规则 ID 与纪律文本不再常驻占据首屏。
4. 风控 CSS 不出现页面私有颜色、字号、间距、圆角或阴影值。
5. 原交易正文成功保存后，所有关联案例的“来源复盘”自动更新。
6. 案例自己的“案例沉淀”正文在任何来源同步中保持不变。
7. 刚编辑正文后立即提炼，案例仍获得最新正文。
8. 原交易不存在时，案例最后同步快照和附件仍可读取。
9. 历史案例不发生自动内容删除或覆盖。
10. 全部相关单元、浏览器、响应式、数据可靠性和生产构建检查通过。
